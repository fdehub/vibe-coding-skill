# 已有项目修改与修复专项

## 先分两条路径

新增／修改功能：原有行为 → 希望变化 → 必须保留的行为。

故障修复：触发步骤 → 预期行为 → 实际现象 → 完整报错／证据。原因未确定时先调查，再依据证据做最小修复；候选原因标为待验证假设。

## 关键规则

- 目标：描述具体差异，不将局部任务改写成重建产品。
- 视觉：默认沿用现有风格；仅说明修改区域和状态。纯逻辑修复无需生成新视觉方案。
- 技术：现有仓库、分支、可访问文件、运行环境、相关日志和启动／测试命令。执行 AI 应先读取适用工程说明与相关调用链，不能因为熟悉某框架就替换现有栈。
- 功能：将复现、定位、最小变更和验证对应起来；新增接口或字段才补充相关契约。不机械要求先做 mock 再接真实数据。
- 约束：指定不动的模块、兼容行为和用户未提交修改；必要数据变更要说明影响，不顺手格式化整个仓库或改无关依赖。重构仅在任务要求或完成修复不可避免时纳入，并解释范围。
- 验收：原先失败的场景得到修复，并针对受影响路径检查回归。无现成测试环境时说明可做的验证与限制，不伪造通过。

## 取证与交付

有路径或日志可读取时先用现有材料，避免让用户重复复制。用户只求提示词、当前拿不到工程时，把有边界的调查交给下游执行 AI，不要求用户手填架构细节。

交付通常是变更、原因、验证结果和必要限制；不能为修一个提交按钮额外要求生产发布、登录系统或整份 PRD。授权仅为修复时，不把部署和数据清理写成默认执行步骤。
