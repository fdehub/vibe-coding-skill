# 开发、验证与调试闭环

在用户要求实现或修复时读取。交付目标是本轮范围内可运行且有证据的结果；请求仅为提示词时，把相关要求写入提示词，不执行开发。

## 1. 从工程事实开始

先读取适用的工程说明、工作区修改、相关调用链、现有接口／数据约定、依赖清单和实际可用的检查命令。保留用户未提交工作，避免顺手替换框架、整仓格式化或扩展重构。

新项目先选择满足目标的简单实现；已有项目优先复用既有模式。技术选型由约束驱动，不默认引入登录、数据库、支付、AI 或部署平台。只查当前任务涉及的官方文档，不把整个仓库和所有参考资料塞进上下文。

当存在会改变产品或数据后果的歧义时，提出最关键的决策问题，同时继续不依赖答案的调查。普通命名、组件拆分等工程细节自行处理。已有授权范围内不增加逐步批准关卡。

## 2. 把较大需求拆成可演示的小闭环

每个任务说明：

- **结果**：用户做什么之后能得到什么。
- **输入与契约**：本任务真正需要的字段、校验、状态变化或接口。
- **范围与依赖**：会影响哪些模块、必须先完成什么；文件位置以当前工程为准。
- **验收**：给定数据、操作、可观察结果，以及如何检查。

例如“个人待办，支持新增、持久化和筛选”可以先实现“输入合法标题→保存→列表出现→刷新仍在”，再实现“切换完成状态→筛选结果正确”。第一块已经能验证价值，不等所有页面完成才跑流程。这只是示例，不是所有产品都要做待办或使用本地存储。

对共享结构的大规模迁移，若小块不能保持兼容，应先增加兼容形式，再迁移调用方，最后移除旧形式；不能承诺每一块独立可用却忽略真实依赖。两行样式修改直接完成，无需任务卡文件。

## 3. 实现一块，检查一块

先打通当前最重要的用户路径，再处理与其相关的失败与边界。复用已有组件、业务服务和错误处理。接口未接入时明确模拟的范围；不能把硬编码成功提示当成真实保存、付款或模型生成。

验证随改动选择：

| 改动 | 有效的验证 |
|---|---|
| 业务逻辑／计算 | 具体输入对应预期输出，覆盖改变结论的边界 |
| 数据读写 | 写入后重新读取，必要时检查重启／刷新后保留；多人产品检查数据归属 |
| 接口集成 | 按真实契约检查请求、响应与业务状态；必要时查异步最终结果 |
| 界面与交互 | 在目标视口渲染并实际操作；视觉任务检查截图、溢出、焦点与反馈 |
| 小范围文案／样式 | 针对变动区域预览或检查，不强制增加单元测试 |

遵守工程必需检查。对有回归价值的逻辑或缺陷，在合适的测试边界补测试；不为可逆的小改动写只复述实现的测试。纯静态检查不能替代关键运行验证。环境缺失时做能够完成的检查，写明缺什么、哪些结论仍未验证。

## 4. 出错先缩小问题，再改代码

记录触发输入、预期结果、实际结果与完整错误位置。先复现用户的具体故障；若不能稳定复现，收集与故障有关的日志或状态，避免把猜测写成根因。

建立尽量短的反馈回路：已有失败测试、最小请求、固定输入的 CLI，或浏览器中的准确操作路径。依据数据流逐段确认问题发生在哪个边界，然后提出一个可以被验证／否定的假设，做足以验证它的变更。

修复后重新跑原失败路径，检查受影响行为，并删除仅为调查添加且不需要保留的临时代码。不要通过禁用校验、吞异常、跳过失败测试或返回伪成功掩盖故障。

同一故障连续两次修补没有带来新证据时，暂停继续猜改，缩小复现、检查假设或调查依赖。无副作用的验证与调查可以继续；付费请求、通知、数据写入等结果未知时先查状态，不盲目重试。若确实缺权限或外部依赖，交付已完成工作与具体缺口，不宣称完成。

## 5. 按证据收尾

复查最终差异是否对应本轮目标，是否误改其他功能。正常路径通过后，完成与当前任务有关的边界、回归及工程要求；没有新改动或未解疑点时不无限增加检查。

简要交付：实现了什么、怎样运行／查看、实际做了哪些验证及结果、尚未接入或未验证的部分。必要时附文件、截图或日志位置。验证结果应对应最终代码，不能用修改前的成功结果证明修改后的状态。

用户要求正式发布时按主文件的领域路由读取上线参考并执行；只要求本地实现时在本地完成交付。达到本轮验收即结束，不自动添加下一阶段产品功能。
