# 游戏专项

## 引导顺序随已知信息调整

只知道“小游戏”时，首先澄清想要的玩法或参考游戏；不要先选技术栈或擅自决定游戏类型。用户已给出核心玩法时，直接补最关键的规则、设备或范围，不再要求从类型选起。

如果用户没想好，先问期望的体验：动脑、反应、操作、经营成长、剧情选择等；必要时提供少量候选帮助表达。这些是选项，不是固定分类或默认选择。

## 关键规则

- **目标**：谁玩、希望获得什么体验、本轮验证什么玩法。简单娱乐不必硬编商业痛点或市场假设。
- **视觉**：风格、视角、场景与关键反馈；素材来源和临时素材边界。游戏方向没定前不要擅自指定像素、卡通或某个参考游戏。
- **技术**：已确认的平台与输入设备、运行环境；按玩法需要选择引擎或网页方案，不自动做多人联网、账号和服务器。
- **核心功能**：玩家反复做的核心动作；操作输入、规则变化、计分／胜负／结束条件；有需要时明确关卡、资源、随机性、碰撞或回合规则。只补当前玩法实际涉及的机制。
- **状态**：开始、游戏中、暂停、结算、重开之间的转换；仅在玩法需要时有失败、存档或成长系统。
- **约束**：本轮内容量、可用素材、设备限制、是否离线；不默认为小游戏增加排行、广告、内购和社交。
- **验收**：用可重复的操作序列验证规则、结束与重开；涉及随机性时提供固定种子或可控样例；按目标设备检查输入、反馈和流畅度，不虚构未经测量的性能结果。

## 组合

新玩法的最小试验可叠加原型专项；存档／关卡编辑才按需叠加数据专项；只有产品运行中真的调用模型才叠加 AI 专项。通过编程 AI 制作游戏，不代表游戏需要 AI 角色或模型接口。
