# 上线交付专项

仅在用户明确要发布、多人正式使用、部署迁移或运营准备时使用。功能变多、接了 API、想做完整 Demo，都不自动等于上线。

## 核心决策

先确定目标环境、使用人群、数据与操作后果、现有运行版本。已有平台与发布机制优先，不能把“上线”自动扩张成 Kubernetes、微服务、复杂账户或付费系统。

## 关键规则

- 目标：上线对象、服务范围、最关键业务路径和可接受的限制。
- 技术：目标平台、构建产物、启动与环境变量、服务依赖、域名和持久化位置。按实际部署环境与当前平台文档核对版本、接口和费用条件。
- 功能：区分演示与真正可运营部分；如果有身份与多用户数据，定义认证和数据隔离；无此需求不强行新建账户系统。
- 数据：数据库迁移与兼容、备份、恢复检验、敏感信息与保留范围。静态展示站不需要复制数据库运维清单。
- 可靠性：在实际规模下定义必要的可用性、延迟、费用和容量指标；日志、监控与失败反馈覆盖关键路径。未知规模不虚构并发指标和“生产级”保证。
- 发布：明确发布目标版本、变更范围、发布前检查、发布后冒烟、失败时回退或停用方案。数据迁移若不可逆，不能写一句“回滚即可”掩盖限制。
- 验收：在接近目标环境的配置运行关键业务；验证密钥不进入公开产物、数据在重启后保留，按实际需要检查权限与恢复。明确阻塞发布的问题与可接受限制。

## 执行边界与交付

设计发布方案和实际部署分别记录。实际发布遵守用户的目标与授权，未授权发布时先准备可审查产物和验证结果；已有授权的普通操作连续推进。

交付重点是可复现构建、运行配置、数据变更、验收证据、已知问题与恢复方式；每项须与目标系统有关，不靠罗列安全术语替代实际可验证要求。
