# 原型验证专项

## 核心决策

优先回答：这一版究竟验证什么？是用户是否需要、能否理解结果，还是某种技术是否可行？区分这三者，不能用页面生成证明市场需求，也不能用模拟数据证明算法准确。

选一个具体场景、一条最短用户路径和一个可观察的结束结果。只保留支撑这个实验的功能；是否保留账号、上传、保存等，取决于实验是否需要，不按固定功能名单删减。

## 关键规则

- 目标：验证假设、目标试用者、观察方法。未知成功阈值可提出候选，不能假装用户已经确认。
- 技术：优先降低本轮运行与演示成本；已有栈优先沿用。若用模拟数据，明确位置、样本含义及后续替换入口。
- 功能：端到端演示能够实际操作，关键按钮有真实结果或明确标识的未接入状态。先完成最小路径，不一次请求整个商业系统。
- 约束：本轮不承担哪些生产要求，哪些演示结论不能外推。模拟用户数、付款、模型输出不得伪装成真实业务证据。
- 验收：除点击可用，还写如何观察用户是否理解价值、能否完成任务。技术验证应使用真实最小样本，不能靠 mock 宣布成功。

## 分阶段选择

流程验证可以先用固定样本；验证模型质量则必须接真实输入输出。不要机械要求“全部 mock → 全量数据 → 全部 AI”三阶段。演示结束的下一步是决定假设是否值得继续，不自动扩展成上线工程。

## 场景特有检查

展示结果与用户利用结果完成任务是不同的验证目标。根据本项目的假设选择观察行为：例如展示报告可检查信息是否可读；验证行动支持还应观察用户是否能据此完成下一步决策。样本和成功条件由该目标决定。
