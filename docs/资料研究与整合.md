## 关键纠错与未采用内容

1. **教程中的仓库名和技能名要复核。** 第 7 篇给出 `superpowers/superpowers`、`pi/planning-with-files` 等命令；本次推荐以核对到的 [obra/superpowers](https://github.com/obra/superpowers)、[OthmanAdi/planning-with-files](https://github.com/OthmanAdi/planning-with-files) 为准。并非看到一行安装命令就执行。
2. **技能入口按目标格式实现。** 第 2 篇举 `art`、`design` 等例子，第 6 篇展示 `skill.yaml + instructions.md`；本版采用所用宿主技能创建规范的 `SKILL.md` 与 YAML `name/description`，而不是把任何教程目录都当作通用标准。界面设计候选核对的是 [frontend-design 原文](https://github.com/anthropics/skills/tree/main/skills/frontend-design)。
3. **项目风格一致不等于业务正确。** 第 6 篇“最近一个月订单”的展示实现没有落实对应的时间过滤，示例校验主要匹配字符串，不能证明业务结果。本版要求验收直接覆盖输入、条件和结果，不靠规范检查冒充正确性。
4. **平台主张不跨产品推广。** 第 13 篇涉及 DevFlow 等平台、私有 SDK、阈值、兼容性和比例，缺少本次可核验的一手支撑；未纳入工具选择或命令。文中把 `asyncio.subprocess` 当作规避禁用 fork 的办法，也不足以成为通用建议。
5. **规则优先级不能从教程任意移植。** 第 11 篇的个人／项目规则说明仅作概念启发；具体执行仍服从宿主指令、适用工程约定和用户选择，不把技能抬升为系统指令。
6. **“永久记忆”“生产级”“提升若干倍”不作为承诺。** 本版采用可读取的项目记录和实际验证结果；不会因使用了 Skill 就宣称数据安全、接口接通、产品上线或效果提升。

## 从资料到技能的映射

| 需求问题 | 采用的具体设计 | 落点 |
|---|---|---|
| 用户不知道怎样表达想法 | 一次优先问一个改变方向的问题；事实先查、决定再问 | `references/guided-dialogue.md` |
| 只有泛泛需求，AI 随意发挥 | 先定义用户结果、规则、范围和验收；提示词按任务成文 | `SKILL.md` 第二部分及 `references/development-prompt.md` |
| 任务太大，做完才发现不对 | 按可演示的用户结果拆小闭环，声明依赖 | `references/execution-loop.md` |
| 老工程被重建、设计被重做 | 先读工程事实，沿用技术栈、组件和设计系统 | `SKILL.md` 与已有项目／界面专项 |
| 凭猜测反复改 Bug | 构建短反馈回路，一次验证一个假设；无新证据时换调查方式 | `references/execution-loop.md` |
| 对话中断后丢失决策 | 按需要保存最少状态，恢复时与当前代码核对 | `references/project-memory.md` |
| 看起来完成，实际没有接通 | 区分 mock、接口成功、业务成功与未验证 | 主文件、执行闭环及 AI／工作流专项 |

评审修订后，主文件聚焦引导关键决定、形成具体任务与交付路由；通用工程细节集中在执行参考。资料中的方法转化为具体判断：事实先查、产品决定再问；按最大不确定性安排首个任务；用真实用户路径验收；无新证据时停止猜改；恢复时核对实际工程。8 份领域参考已统一为模式中性的关键规则，不再依赖旧版提示词栏目。

不强制六栏目成文，也不为所有项目增加整套 PRD、审批、多代理和工具安装。用户只要提示词时交付提示词，明确要求实现时完成实现与验证。
